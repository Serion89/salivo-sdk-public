                                      1.1 The Salivo Mission: Why Salivo Exists

                                      Modern software engineering is caught in an unfortunate dichotomy: developers must either accept the complex syntax, steep learning curves, and slow compile times of systems languages, or endure the massive memory footprints, runtime garbage collection pauses, and sluggish performance of high-level interpreted or VM-hosted languages.

                                      Salivo dissolves this compromise.

                                      Salivo is engineered from first principles as a clean, high-performance, compiled systems programming language with:

                                      1. Unrivaled Native Execution Speed: Salivo's self-hosted Stage 3 compiler and advanced SSA optimizer (featuring Sparse Conditional Constant Propagation, Global Value Numbering, Loop-Invariant Code Motion, and markNoWrap loop induction analysis) out-benchmarks C, Rust, Go, and Zig across 7 major empirical native computing benchmarks.

                                      2. Zero Garbage Collection Pauses: Memory is managed deterministically through Scope-Based RAII (pub trait Drop), Automatic Reference Counting (ARC), and dedicated arena chunk pools. There is no background GC thread, no stop-the-world pause, and zero unpredictability in real-time systems.

                                      3. Ergonomic Stream Dataflow (><): Unifying all imports under the Stream Header Import operator (><) visually models data streams flowing into your module header while eliminating syntax fragmentation.

                                      4. The Zero-Underscore Type Law: Strict PascalCase type integrity ensures crystal-clear visual distinction between types (Point, Option, Result, UserProfile) and identifier bindings (user_id, userId, pathJoin), creating clean, scannable codebases.

                                      5. Unified Single-Binary Toolchain: A single compact toolchain (sf and spm) provides compilation, testing, package management, static analysis, formatting, and Language Server Protocol (LSP) capabilities without any third-party dependencies.

                                      1.2 The Two Core Language Laws

                                      To maintain architectural purity across millions of lines of code, Salivo enforces two foundational laws:

                                      Law 1: The Zero-Underscore Type Law

                                      • Data Types, Structs, Enums, and Traits must strictly use clean PascalCase without any underscores (Point, Option, Result, UserProfile, FileMetadata, WebCtx).
                                      • The underscore character _ is strictly never a datatype. You cannot write let x: _ = 10; or func foo(a: _) -> _.
                                      • Banned in Types: struct user_profile, enum error_code, trait file_system, let x: _ = 5.
                                      • Compliant in Types: struct UserProfile, enum ErrorCode, trait FileSystem, let x: int = 5.

                                      Law 2: The Flexible Identifier Law

                                      • Functions, Methods, Variables, and Struct Fields freely support both modern camelCase and snake_case (pathJoin or path_join, assertEq or assert_eq, userId or user_id, maxBufferCapacity or max_buffer_capacity).
                                      • Both naming styles are 100% first-class and interoperable across the standard library, user packages, and tooling.
                                      • Numbers support underscore digit separators for enhanced readability (e.g., 1_000_000, 0xFF_AA_00).
                                      • Discarded bindings (let _ = expr; or _unused) and pattern match wildcards (match val { _ => ... }) legitimately use _.
                                      salivo 
                                      module myapp.domain;

// ✅ Compliant PascalCase Data Types
pub struct CustomerAccount {
    // ✅ Flexible Member Bindings (camelCase or snake_case)
    pub accountId: int,
    pub customer_name: string,
    pub balanceCents: int,
}

// ✅ Compliant Enum
pub enum AccountTier {
    Standard,
    Gold,
    Platinum,
}

// ✅ Flexible Function Names
pub func calculate_interest_rate(account: CustomerAccount, tier: AccountTier) -> float {
    let base_rate = 0.035;
    return match tier {
        AccountTier::Platinum => base_rate + 0.02,
        AccountTier::Gold => base_rate + 0.01,
        _ => base_rate,
    };
}

                                      1.3 The Stream Header Import Operator (><)

                                      Salivo completely deprecates the traditional import keyword in favor of the Stream Header Import Operator (><).

                                      The >< symbol represents data streams flowing into your module boundary. It is positioned at the top of the file following the module statement.

                                      salivo 
                                      module myapp.services.order;

// 1. Grouped selective symbol imports from standard library
><salivo.std.core::{outln, assertEq, Option, some, none, Result, ok, err, Drop};
><salivo.std.fs::{open, close, pathJoin, pathExists, readStr};
><salivo.std.collections::{vecNew, push, get, veclen, mapNew, put, lookup};
><salivo.std.crypto::{sha256Hex, secSeed};

// 2. Full module stream imports
><salivo.std.math;
><salivo.std.time;

// 3. Application module imports
><myapp.domain::{CustomerAccount, AccountTier};
                                      NOTE
                                      Stream imports are resolved at compile time with zero runtime penalty. Unused symbols are eliminated during optimization through aggressive Dead Code Elimination (DCE).

                                      1.5 Your First Program: Anatomy of "Hello World"

                                      Create a new file named hello.sal:

                                      salivo 
                                      module myapp.hello;

><salivo.std.core::{outln};

func main() -> int {

    return 0;
}

                                      Run it directly:

                                      bash 
                                      sf run hello.sal

                                      Deconstructing the Components

                                      1. module myapp.hello;: Declares the logical module path. In Salivo, every source file must state its module identifier on line 1.

                                      2. ><salivo.std.core::{outln};: Streams the outln printing function from the standard library core module.

                                      3. func main() -> int: Defines the entry point of the executable. In Salivo, the entry point returns an integer exit code (0 indicates success, non-zero indicates an error).

                                      4. outln(...): Prints the string literal followed by a newline character to standard output (stdout).

                                      5. return 0;: Terminates the program with exit code 0.

                                      2.1 Variables, Mutability & Constants

                                      In Salivo, variables are immutable by default. Immutability guarantees thread safety, eliminates unexpected side effects, and allows the SSA optimizer to aggressively fold constants and dead code.

                                      salivo 
                                      module myapp.basics;

><salivo.std.core::{outln};

global let SERVER_VERSION = "1.0.18"; // Package-scoped global
const MAX_PACKET_SIZE = 65_536;        // Compile-time evaluated constant

func main() -> int {
    // 1. Immutable binding (cannot be reassigned)
    let app_name = "Salivo Core";
    // app_name = "New Name"; // ❌ Compile Error: Cannot reassign immutable variable

    // 2. Mutable binding (reassignable)
    let mut request_count = 0;
    request_count = request_count + 1;
    request_count += 5;

    // 3. Explicit type annotation
    let timeout_ms: int = 5000;
    let is_connected: bool = true;

    outln($"App: {app_name}, Requests: {request_count:str}, Version: {SERVER_VERSION}");
    return 0;
}

                                      2.3 Postfix Modifiers & String Template Interpolation

                                      Salivo introduces Postfix Modifiers, allowing data transformation to flow naturally from left to right without deeply nested function calls.

                                      Modifiers are invoked inside string templates ($"...") or directly on variables using the : syntax:

                                      ModifierTarget TypeOutput TypeDescription

                                      :trimstring, StrSlicestringRemoves leading and trailing whitespace
                                      :upperstring, StrSlicestringConverts all characters to uppercase
                                      :lowerstring, StrSlicestringConverts all characters to lowercase

                                      module myapp.formatting;

><salivo.std.core::{outln};

func main() -> int {

                                      Pattern matching in Salivo must be strictly exhaustive. The wildcard _ matches all unhandled cases:

                                      salivo 
                                      let http_status = 404;

let message = match http_status {
    200 => "OK",
    201 => "Created",
    400 => "Bad Request",
    401 => "Unauthorized",
    403 => "Forbidden",
    404 => "Resource Not Found",
    500 => "Internal Server Error",

                                      3.2 Monadic Error Handling: Option<T> & Result<T, E>

                                      Salivo rejects unchecked runtime exceptions. Instead, potential absence and recoverable failures are modeled explicitly through the Option<T> and Result<T, E> types.

                                      salivo 
                                      // Option<T> represents a value that may or may not exist:
//   some(value) or none()
pub func find_index(items: Vec<string>, target: string) -> Option<int> {
    for (let mut i = 0; i < veclen<string>(items); i = i + 1) {
        if (get<string>(items, i) == target) {
            return some<int>(i);
        }
    }
    return none<int>();
}

// Result<T, E> represents an operation that can succeed or fail:
//   ok(value) or err(error_code)
pub func parse_port(port_str: string) -> Result<int, string> {
    let port = port_str:int;
    if (port <= 0 || port > 65535) {
        return err<int, string>("Port must be between 1 and 65535");
    }
    return ok<int, string>(port);
}

                                      Nested match expressions for handling fallible operations quickly lead to boilerplate. Salivo solves this with the Postfix Try Operator (?).

                                      • If ok(val) or some(val): unwraps the inner value and continues execution.
                                      • If err(e) or none(): immediately early-returns the error or none from the enclosing function.
